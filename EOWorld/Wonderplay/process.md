# 本周工作总结

本周主要完成了 WonderPlay 交互式场景模拟、多视角扩展以及视频优化流程的整合。

1. 完成前端交互式逻辑与 OBJ/ENV 交互模拟流程的打通。前端通过 Flask-SocketIO 与后端通信，支持用户输入场景提示词、设置 SAM3 的运动区域文本提示、点击选择运动区域、绘制运动箭头、调整环境运动幅度以及切换相机视角。用户确认运动标注后，后端根据交互方向分别处理 `obj2env` 和 `env2obj` 场景：使用 SAM3 从当前图像中分割需要运动的环境区域，再结合用户绘制的起点和终点轨迹，通过 Cinemagraphy 估计二维运动场，并将二维光流绑定到当前环境点云的三维 Gaussian 上。随后训练 HashGrid 运动模型，驱动 OBJ 和 ENV 的三维位置随时间变化，并实时渲染交互模拟结果和预览视频。

2. 针对重复场景重建过程增加并梳理运行时中间结果复用机制。对于已经完成初始化的场景，通过 `work_dir/model` 下的 `finished_3dgs.ply`、`visibility_filter_all.pth`、`is_sky_filter.pth`、`delete_mask_all.pth` 和 `scene_state.pt` 恢复固定场景的 Gaussian、关键帧、物体信息、相机参数及场景状态，在开启 `load_gen` 后可以跳过场景重建。对于场景分析和关键帧处理，复用了 `semantic_map.pt`、`sky_mask.pt`、`depth_initial.pt`、`disparity_initial.pt`、`sam_masks.pt` 和 `base_layer.png` 等缓存文件；对于天空生成，复用了 `sky_0.png`、`sky_1.png` 以及 `finished_3dgs_sky_tanh.ply`，避免重复执行语义分割、深度估计、SAM 分割、前景移除、背景补全和天空点云生成。视频条件构建阶段则以已有的 `traj_00/frames`、`traj_00/flows_actual` 和 `traj_00/noises.npy` 为基础，其中 `noises.npy` 是由实际光流经过 NoiseWarper 生成的结构化噪声，在条件未发生变化时可以直接复用，从而减少重复计算并加速场景恢复和视频生成。

3. 实现基于新相机视角的多视角扩展运动。系统接收前端传入的相机位姿，在新视角下分别渲染包含天空和不包含天空的场景，计算扩展区域、填充区域和空洞区域的掩码，并保存 `generation_condition.png`、`generation_fill_mask.png` 和 `generation_hole_mask.png` 等扩展条件。随后调用图像补全模型生成新的环境内容，更新天空掩码、深度和视差，并通过点云反投影将补全区域转换为新的 Gaussian 点云。新生成的环境点云经过局部 Gaussian 训练后，仅追加到原有环境 Gaussian 中，同时保持已有 OBJ 与 ENV 的点云划分和交互状态不变。每次扩展结果以 `multiview_XXX` 目录保存，支持用户连续切换视角、扩展场景并继续进行交互模拟。

4. 在多视角扩展和交互渲染结果的基础上接入视频优化流程。系统首先生成模拟 RGB 帧、深度图、物体掩码、光流图和 `flows_actual/*.npy`，再通过 RAFT 计算和整理视频光流，并利用光流生成 RealWonder 所需的结构化噪声。视频优化阶段同时使用原始首帧、模拟视频帧、文本提示词、光流结构化噪声以及模拟视频经过 VAE 编码得到的 latent，通过 SDEdit 方式保持原始场景外观和结构，改善多视角扩展区域的画面质量、运动连续性、时序稳定性和视觉一致性，最终输出细化后的视频及逐帧结果。

# 9/6 进度：
1. 尝试单独加入SDEdit，但是效果一般，查阅文档发现diffusers 框架中的包就是使用了SDEdit可以直接使用的。下一步觉得应该先利用视频监督3D场景的更新，因为现在generate_condition 这张图片本来就很模糊，这个模糊会进一步继承到下一步中，所以如果3D场景比较清晰的话，应该也会有利于做outpaint。

2. 完成“视频模型细化结果监督动态 3D 场景更新”的基本闭环。物理模拟首先输出粗动态 3D Gaussian 序列和对应渲染帧，RealWonder 使用模拟帧、首帧、文本提示和结构化光流噪声生成细化视频。细化视频不再直接作为最终前端播放结果，而是作为固定的二维监督信号，通过可微 Gaussian Renderer 重新渲染每一帧动态 3D 场景，并按照论文中的基本目标计算光度 L1 损失：`L = |V - Render(S)|_1`。优化变量包括每帧前景物体 Gaussian 的三维位置、前景物体的颜色特征，以及每个背景 Gaussian 的颜色特征。当前没有加入 SSIM、前景区域加权、物理轨迹锚定、时间平滑、最大位移约束、首帧冻结或跨帧参数初始化等额外方法，以便先验证论文原始方法的实际效果。

3. 统一视频监督和动态 3D 场景的时间长度。RealWonder 默认使用 12 个时序 latent，解码后产生 `12 × 4 - 3 = 45` 帧 RGB 视频；原交互流程生成 50 个模拟状态，之前需要将 45 个视频帧线性映射到 50 个模拟状态，这并非论文方法。现在交互模拟、粗 3D 渲染、RealWonder 输出和视频监督优化均统一为 45 帧，第 `t` 个生成视频帧严格监督第 `t` 个动态 3D 状态。若两者帧数不一致，优化阶段会直接报错，不再进行插值或自动映射。当修改 RealWonder 的 `num_output_frames` 时，交互流程会按照 `4 × num_output_frames - 3` 自动设置所需的 RGB 帧数。

4. 将优化后的动态 3D 场景接回前端播放。优化阶段会保存每帧物体位置、物体颜色和背景颜色，并生成 `video_supervised_3d/optimized_dynamic_scene.pt`；同时重新渲染优化后的 3D 场景，输出 `optimized_3d_frames/` 和 `optimized_3d_scene.mp4` 供检查。前端播放时不直接读取 RealWonder 的二维视频，而是读取内存中的优化后动态 3D 参数，根据用户当前相机视角在服务端实时渲染并通过 SocketIO 发送到浏览器，因此切换视角后仍然播放的是三维场景渲染结果。

5. 修正视频生成阶段对梯度状态的影响。RealWonder 的 VAE 编码和视频推理被限制在 `torch.inference_mode()` 中，完成生成后，三维场景优化阶段重新开启梯度，确保 L1 损失可以通过 Gaussian Renderer 反向传播到物体位置及前景、背景颜色参数。

6. 现在的优化代码只优化物体的位置、颜色以及背景的Gaussian颜色，无法优化水面的高频纹理。

7. 目前遇到的核心问题总结：
(1) 无法优化水面的高频纹理及运动细节，整体画面略显模糊。
(2) 前后端暂停时的画面不一致
(3) 场景扩展内容极差，好像在进行场景扩展后又继续完成的obj与env的分离操作会影响扩展画面，此处逻辑混乱，应仔细检查，最好能够利用SAM点击进行选择。
(4) 双卡运行模式暂未启动

8. 环境运动残差的视频监督优化方案。当前水面属于环境 Gaussian，初始运动轨迹由用户标注的二维光流、场景流和 HashGrid 运动模型共同得到，记为粗环境轨迹 `e_t^0`。视频模型生成的细化视频可以作为二维监督信号，但目前的优化阶段只更新物体轨迹和颜色，没有更新环境位置，因此水面的运动仍然沿用原始 HashGrid 结果。后续可以在每一帧的环境轨迹上增加可训练残差 `Delta e_t`：

   `e_t = e_t^0 + Delta e_t`

   其中 `e_t^0` 是物理模拟和 HashGrid 预测的环境 Gaussian 位置，`Delta e_t` 是视频监督学习到的水面运动修正。将 `e_t` 与物体位置 `o_t` 一起送入可微 Gaussian Renderer，得到当前动态 3D 场景的渲染结果：

   `I_t = Render(o_t, e_t, c_t)`

   再使用 RealWonder 输出的视频帧 `V_t` 计算论文中的光度监督损失：

   `L_video = sum_t || V_t - I_t ||_1`

   通过 `L_video.backward()`，梯度可以沿着 `e_t -> Render -> I_t -> L_video` 的路径反向传播到 `Delta e_t`，从而直接调整水面 Gaussian 的三维位置和运动轨迹。优化结束后保存每帧的 `e_t`，前端播放时使用优化后的物体轨迹和环境轨迹重新渲染，而不是直接播放 RealWonder 的二维视频。

   该方案是对论文基本方法的针对性扩展：论文明确使用生成视频监督动态 3D 场景，并优化前景动态对象及背景颜色；当前工程中的水面被放在环境分支，因此需要额外把环境位置残差加入优化变量。第一阶段建议只优化被 SAM3 水面 mask 选中的环境 Gaussian，保持天空和静态建筑不变，以验证视频监督是否能够改善水面运动；如果有效，再考虑将残差从逐帧位置扩展为共享的环境流场或 HashGrid 参数。
